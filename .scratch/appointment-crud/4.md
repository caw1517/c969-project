## What to build

Delete the selected appointment after confirmation and refresh the grid, with a dedicated Delete failure path.

## Acceptance criteria

- [ ] Require a selected appointment. Ask Yes/No with No as the default; declining or having no selection changes nothing.
- [ ] Delete only that appointment by its stable ID using parameterized SQL; preserve the Customer, User, and all other appointments.
- [ ] Report a missing row appropriately instead of claiming it was deleted.
- [ ] Catch database failures in a Delete-specific exception path and keep the application usable.
- [ ] Refresh after successful deletion and distinguish a successful delete followed by refresh failure from a failed delete.
- [ ] Build and verify confirmed deletion, declined deletion, no selection, preservation of related records, and a controlled Delete failure in the running app.
